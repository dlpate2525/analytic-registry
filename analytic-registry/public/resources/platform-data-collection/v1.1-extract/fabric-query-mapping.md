# Fabric query handoff

Query revision: **2**, reviewed **9 October 2026**. Contract: **V1.1, 11 tables and 72 columns**.

Use [fabric-inventory.sql](queries/fabric-inventory.sql) to query a supplied Fabric inventory snapshot in a Fabric Warehouse or Lakehouse SQL analytics endpoint. The file contains no API calls. It produces the existing workbook headers and preserves native report, semantic model, and workspace IDs.

The input table is an adapter owned by your organization. It must be populated from actual inventory evidence before the query can run. This pack does not claim that `registry_source.FabricInventory` exists in Fabric by default.

## The platform distinction

Fabric's SQL analytics endpoint queries the Delta tables in a lakehouse. It is not a SQL catalog of every report and workspace in the tenant. Creating a lakehouse does not make tenant administration records available as SQL tables. This is the reason for the explicit inventory adapter. [Microsoft: SQL analytics endpoint](https://learn.microsoft.com/en-us/fabric/data-engineering/lakehouse-sql-analytics-endpoint)

For a query-oriented source, use the estate inventory in **OneLake catalog → Govern**, when available. Microsoft supports creating a custom report from its autogenerated semantic model. The estate data refreshes daily; it is not live platform state. Do not alter the original managed report or model. Microsoft does not publish a fixed SQL or DAX table schema for this model in its documentation. The DAX names must therefore be discovered in the installed model. [Microsoft: Govern your data estate](https://learn.microsoft.com/en-us/fabric/governance/onelake-catalog-govern)

The older **Feature usage and adoption** model also exposes item and workspace IDs. Microsoft now recommends Govern; the older report remains in preview and will not gain additional data. Its activity status means recent audit activity, not account status or item lifecycle. Do not copy that status into `NativeLifecycleCode`. [Microsoft: Feature usage and adoption](https://learn.microsoft.com/en-us/fabric/admin/feature-usage-adoption)

## Prepare the source once

1. Open the installed inventory model through an approved query or custom-report connection.
2. Inspect its field list or run the discovery DAX query where permitted.
3. Map the real fields to the adapter columns below.
4. Validate the source snapshot against a known report and semantic model.
5. Save the adapter mapping with the delivery evidence.

`INFO.VIEW.COLUMNS()` returns the connected semantic model's column metadata. It does not return tenant items. The extraction template stays commented until the actual table and column names are known. A managed model can restrict query access; in that case, use its permitted custom-report field list. No guessed table name is supplied as executable source SQL. [Microsoft: INFO.VIEW.COLUMNS](https://learn.microsoft.com/en-us/dax/info-view-columns-function-dax)

## Adapter input: `registry_source.FabricInventory`

One row represents one item in one immutable source snapshot. This is a landing shape, not a new registry entity. A view over existing landed inventory is preferable to copying the same data again.

| Input column | Landing SQL type | Required meaning |
|---|---|---|
| `RunKey` | `varchar(max)` | Existing delivery UUID. Use one immutable snapshot per run. |
| `WorkspaceId` | `varchar(max)` | Actual native workspace ID. Never a name or row number. |
| `WorkspaceName` | `varchar(max)` | Workspace display name observed in the snapshot. |
| `WorkspaceType` | `varchar(max)` | Validated native workspace type. Preserve the namespace used by earlier accepted scans. Do not guess a personal workspace's type. |
| `ItemId` | `varchar(max)` | Actual native report or semantic model ID. A recreated item has a new ID. |
| `ItemName` | `varchar(max)` | Item display name observed in the snapshot. |
| `ItemType` | `varchar(max)` | Validated source type. `Report` stays `Report`; `SemanticModel`, `Semantic model`, or `Dataset` maps to registry native type `Dataset`. |

Land text without truncation. The query checks destination limits before output: IDs and names allow 200 UTF-16 code units; workspace type allows 50. Oversized values stop the batch for review. Use case-sensitive UTF-8 text columns, such as `Latin1_General_100_BIN2_UTF8`, to preserve IDs and Unicode names. Store GUIDs as text for consistent Warehouse/Lakehouse export behavior. Fabric documents limitations when persisted `uniqueidentifier` values cross these engines. [Microsoft: Fabric data types](https://learn.microsoft.com/en-us/fabric/data-warehouse/data-types)

If the inventory model omits workspace type, obtain it from an existing approved workspace inventory and join by workspace ID. A missing required source field stops extraction. It does not justify inventing a value. Do not join by workspace name.

## Monthly extraction

1. Save the source snapshot, its scope, and its source refresh time.
2. Load the snapshot into the adapter using the existing `RunKey`.
3. Set the SQL manifest parameters and run the full batch.
4. Save each named result in its matching workbook table.
5. Check saved counts before accepting the delivery into SQL Server.

Set `ObservedAt` to the source observation or refresh time, with an explicit UTC offset. Do not replace it with the later SQL execution time. Preserve the existing `PlatformInstanceKey`, tenant, and scope namespace across refreshes. The SQL file deliberately keeps `PlatformCode=PowerBI` and asset type `Dataset`; changing these to `Fabric` and `SemanticModel` would create different registry identities.

Run the full batch in one session without an existing transaction. The query uses one explicit read transaction for validation, extraction, and counts. Fabric applies snapshot isolation. Keep the landed delivery immutable after sealing it; a changed snapshot requires a new run. If any statement fails, discard every output from that attempt. [Microsoft: Fabric transactions](https://learn.microsoft.com/en-us/fabric/data-warehouse/transactions)

Power BI query grids and visual exports can truncate results. Confirm the row count and any applied filters. Split large outputs by explicit workspace scope when needed; retain the partition manifest. A successful query or an Excel file is not proof of full coverage. [Microsoft: DAX query view](https://learn.microsoft.com/en-us/power-bi/transform-model/dax-query-view), [Microsoft: export data](https://learn.microsoft.com/en-us/power-bi/visuals/power-bi-visualization-export-data)

## Output coverage and NULL rules

| Workbook dataset | This Fabric query provides | Coverage |
|---|---|---|
| `Run_Context` | Existing run and scope parameters | One manifest row |
| `Workspaces` | Native IDs, names, and validated native types for represented workspaces | `Partial`; empty workspaces are not represented by item inventory |
| `Assets` | Report and semantic model IDs and names | `Partial`; scoped to these item types and the supplied snapshot |
| `Workspace_Assets` | Direct item-to-workspace membership | `Partial`; `ContainedIn` retains the prior relationship code |
| `Connections` | Header only | `NotCollected` |
| `Asset_Connections` | Header only | `NotCollected` |
| `Asset_Dependencies` | Header only | `NotCollected` |
| `Platform_Users` | Header only | `NotCollected` |
| `Object_Users` | Header only | `NotCollected` |
| `Directory_Users` | Header only; supplied separately from the directory | `NotCollected` |
| `Coverage` | Nine dataset records; emitted counts for Partial and NULL counts for NotCollected | Three `Partial`, six `NotCollected` |

`NativeVersionReference` and `NativeLifecycleCode` remain NULL because this source shape does not establish them. A missing connection, user, or dependency is **uncollected evidence**, not evidence that no relationship exists. Never infer report-to-model lineage from matching names or co-location. Never treat a modifier or activity user as the current owner.

This deliberately narrow route supports a first inventory load. It cannot support complete access reconciliation, connection controls, or deletion decisions. If the team requires those controls, use the richer supplied metadata export query or provide additional verified source tables. The registry's email-resolution process remains unchanged and waits for actual principal and directory evidence.

## Validation status

The supplied Fabric SQL is a projection contract, not a verified tenant connector. It includes guards for missing manifest context, missing native IDs, conflicting workspace attributes, and duplicate asset keys. It emits all 11 workbook result shapes. The DAX file contains a runnable discovery query and an intentionally unbound extraction template.

The local [Fabric handoff checks](queries/verify-fabric.mjs) passed **18 checks** for workbook header order, stable namespaces, coverage states, read-only query content, and transaction boundaries. These are static contract checks, not SQL or DAX execution tests.

No tenant model, Fabric database, or real inventory snapshot was available for live execution. The platform manager must verify the source mapping and execution in the target environment before marking a delivery accepted. There is no invented Fabric release number or claimed internal database schema.
