# Analytic Registry V1.2 — requirements and boundaries

**1.2.0-prototype.1 · Prototype release · 21 October 2026**

This document describes the current local application. The [product guide](v1.2-guide.md) explains its pages and workflows. The [verification record](v1.2-publication-verification.md) states which checks ran.

**Implemented locally** means behavior in the React prototype with browser storage and fictional records. It does not establish production security or live source compatibility.

**Intended integration** means an agreed operating requirement or design that is not connected to the application. **Unresolved policy** means a choice still needs approval.

## Implemented functional behavior

| ID | Requirement | Local acceptance behavior |
|---|---|---|
| F-01 | Keep navigation compact | Five primary sections; administration in a menu; guided forms have fewer than six steps |
| F-02 | Show clear page actions | Lists identify mapped Workspace and Asset where applicable; missing associations remain explicit |
| F-03 | Use one Workspace Owner and equal Champions | No Champion hierarchy or second business-owner field; business line is declared separately from directory context |
| F-04 | Separate responsibility from permissions | Champion authority does not grant platform access; Standard has Champion, RW, R, and `_DS` group purposes |
| F-05 | Support three request types | Create New, Register Existing, and Update Existing preserve platform and workspace context |
| F-06 | Limit forms to relevant fields | Existing business-only requests have three steps; Create New and technical requests have five |
| F-07 | Apply the approved Champion policy | One eligible current Champion approves business declarations and Owner/Champion changes; eligible proposed Champions can approve initial setup |
| F-08 | Retain additional approval requirements | Custom requires Application Owner or Platform Owner approval; applicable technical work requires Platform Administrator approval |
| F-09 | Apply business responsibility by approval and date | Effective assignments route new work; approved business changes can complete while applicable technical work remains open |
| F-10 | Preserve submitted intent and earlier decisions | Corrections create linked drafts; historical requests retain their policy and approval receipts |
| F-11 | Keep source facts separate from business context | Observed names, native revisions, memberships, and connections do not become approved business declarations |
| F-12 | Maintain one accountable workspace per asset | Initial confirmation requires an eligible Champion; a Platform Manager transfer requires recorded business confirmation |
| F-13 | Preserve association history | Association changes retain native memberships, completed evaluations, and existing cases |
| F-14 | Record completed asset evaluations | An eligible current Champion completes four steps; there is no saved draft, asset approval queue, or asset Annual Attestation |
| F-15 | Use explicit business versions | Material business changes create a new version with its evaluation; historical evidence cannot replace current context |
| F-16 | Calculate PRL through PRL-01 | Complexity, logical source count, and intended audience determine PRL; unknown applicable inputs remain explicit |
| F-17 | Apply the agreed High risk rule | PRL 1 OR PII Yes OR EUCT Yes OR DMP Tier 1–3 qualifies; qualification does not create a Review case automatically |
| F-18 | Keep shared work consistent | My work uses the same task records for counts and filters; URL filters persist; unresolved responsible IDs remain visible |
| F-19 | Preserve annual packet context | Three-step Annual Attestation retains frozen recipients and context; completion needs Application Owner or Platform Owner approval |
| F-20 | Keep evidence closure separate | Three-step Review cases require eligible approval of exact closure evidence; completed cases are read-only |
| F-21 | Show evidence limitations | Coverage and evidence age remain visible; unknown evidence is not treated as a passing control |
| F-22 | Explain manual ingestion without implying automation | Platform imports links queries and the workbook; synthetic comparisons do not write a source delivery into the registry |
| F-23 | Keep retired records available | Retired workspaces are hidden by default and can be included; no retirement or restoration operation is provided |
| F-24 | Separate coverage and risk meanings | One current catalog covers all 11 retained buckets across four themes; historical capability samples do not drive current availability claims |
| F-25 | Connect findings to explicit work | Finding status is visible and URL-backed; Review-case links use explicit finding IDs and preserve historical relationships |

The guide contains the complete [PRL decision table](v1.2-guide.md#complete-governance--risk). Tier 1 is the highest DMP tier. Untiered differs from Unknown.

Local business commands validate actors, relevant dates, record context, and stale state. Profile simulation remains separate from a production identity service.

## Nonfunctional requirements

| ID | Requirement | Current boundary |
|---|---|---|
| N-01 | Use a consistent tablet canvas | Fixed 1366 × 768 design coordinates with proportional scaling and internal scrolling |
| N-02 | Keep the interface clear | White backgrounds, purple and coral accents, reusable fields, direct labels, and visible next actions |
| N-03 | Protect saved records | Loading errors preserve original data; browser migration retains historical records; reset requires an explicit action and retains recovery data |
| N-04 | Prevent stale updates | A stale browser write is rejected instead of silently overwriting newer data; relevant command authority is checked again at save |
| N-05 | Preserve evidence meaning | Observation time, business effective date, and recording date remain distinct; older evidence does not silently become current |
| N-06 | Support local regression checking | TypeScript, domain checks, local builds, and disposable browser journeys validate the prototype; results belong in the verification record |
| N-07 | Make controls understandable | Forms have labels, explicit validation, and keyboard navigation support; no formal accessibility certification is claimed |
| N-08 | Keep identity stable | Preserve Registry IDs, native identity components, historical actors, and unresolved references; names do not become join keys |
| N-09 | Limit sensitive metadata | Source queries select required metadata; credentials and secrets are outside the contract; production export controls still need implementation |
| N-10 | Keep delivery local | Current validation and artifacts stay local; no deployment, release publication, or GitHub push is part of this revision |

Production availability, performance, recovery, and accessibility targets are not certified by local tests. The local prototype is not a shared transactional database.

## Intended integration and operating requirements

| ID | Requirement | Available artifact or gap |
|---|---|---|
| I-01 | Collect platform evidence at least monthly | Workbook revision 1.2 uses input schema 1.1 and existing query references; no recurring collector is deployed |
| I-02 | Use the agreed source inputs | Tableau PostgreSQL; Alteryx Gallery/Service exports in SQL Server; landed Power BI/Fabric inventory; installed execution remains unverified |
| I-03 | Keep compatible source delivery | Use `analytic-registry-v1.2-extract.xlsx`; retain 11 input tables, 72 headers, types, and keys. The 72-row dictionary and three platform tabs provide separate reference views |
| I-04 | Stage and validate the complete delivery | SQL staging and diagnostic scripts exist; structural errors block the whole delivery; a transactional registry loader is not connected |
| I-05 | Accept valid evidence with explicit gaps | Registry operator accepts structurally valid Partial evidence and unresolved references; Platform Manager receives unresolved follow-up |
| I-06 | Preserve replay and chronology | Keep immutable RunKey/content identity, source scope, coverage, and observation time; changed content under one RunKey is rejected |
| I-07 | Resolve source users against directory evidence | Compare normalized SourceEmail to Mail within one tenant; preserve disabled, ambiguous, missing, and failed outcomes separately |
| I-08 | Use durable identity mappings | Keep native IDs separate from Registry IDs; multiple source accounts can bind to one Person; groups and applications remain principals |
| I-09 | Protect business metadata during refresh | Source updates affect technical observations; approved responsibility, evaluations, approvals, and open work keep their own authority |
| I-10 | Maintain a persistent issue history | Repeated source occurrences should reuse stable issue identity; failed collection cannot close an issue; no production case-upsert service is deployed |
| I-11 | Apply the agreed history objective | Retain six calendar months of superseded metadata while preserving current identity, open work, and active evidence; no retention job is implemented |
| I-12 | Implement production access checks | Enforce authentication, authorization, approvals, and transactions on the server; browser profile controls are simulations |
| I-13 | Provide a deployable Power Apps solution | SQL Server remains the selected target; the offline Canvas deliverable is unfinished and not import-tested |

Use the [extract handoff](../../platform-data-collection/v1.2-workbook/README.md) and [monthly procedure](../../platform-data-collection/v1.1-extract/monthly-reconciliation.md) for detailed delivery rules.

The proposed foundation entities and historical operational models are design references. They are not the application's deployed schema or proof of SQL Server compatibility.

## Unresolved policy and deferred scope

These items remain separate from defects. V1.2 does not introduce a new rule merely to close a documentation gap.

| Topic | Decision or work still needed |
|---|---|
| Annual Attestation | Complete the scheduling, response, reassignment, and overdue-policy review; retain existing frozen-packet behavior meanwhile |
| Retirement | Define request, approval, platform action, restoration, and evidence rules before adding lifecycle operations |
| Freshness | Approve evidence-age thresholds by dataset or control; monthly collection alone does not establish sufficiently fresh control evidence |
| Shared cases | Define any additional case grouping, ownership, reopening, and linked-object rules beyond existing behavior |
| Effective-date edge cases | Resolve late-approval precedence and retrospective implementation-date policy before changing current workflow semantics |
| Shared data sources | Deferred: cross-platform endpoint matching and a separate common DataSource entity; keep details on each connection |
| Live source acceptance | Inspect actual exports and execute queries against the installed sources before claiming compatibility or complete coverage |

The [accepted ADRs](adr/0001-effective-business-responsibility.md), [partial-evidence decision](adr/0002-accept-valid-evidence-with-visible-gaps.md), and [registration boundary](adr/0003-separate-business-registration-from-technical-work.md) retain their accepted meaning.

Older manuals and decision registers remain historical records. Use this document and the [V1.2 guide](v1.2-guide.md) for current local behavior.
