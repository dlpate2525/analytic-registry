# V1.1 product and operating-model review

**Review date:** 9 October 2026. **Method:** source inspection of the React runtime, collection handoff, V1.1 foundation, and documented decisions. Browser and live-platform testing are not claimed here.

The product should make a monthly metadata delivery trustworthy, then turn material exceptions into clearly assigned work. It currently demonstrates several governance workflows well, but those workflows are ahead of the ingestion and registry-update path. The highest-value next release is a consistent evidence-to-decision loop, not more forms or risk rules.

**Fact** means directly observed in the cited code or artifact. **Inference** states a product consequence. **Recommendation** is a proposed change. This revision separates implemented repairs from remaining operating gaps. See the [V1.1 verification record](v1.1-verification.md) for final regression, browser, workbook, and artifact checks. No live tenant test is claimed.

## 1. What the product must stop implying

The app is a registry and coordination tool. It does not provision analytics resources, grant directory access, or collect platform evidence. Request approval, an implementation receipt, and an accepted source snapshot are different records.

The code already states this boundary in several places. The remaining problem is that dashboard counts and completion language can imply a more complete operational result. A user should be able to answer “what is now true in the registry?” after every completed action.

[Reference comparison](../src/domain/foundation.ts), [page](../src/pages/DataFoundation.tsx) | **Inference:** the new schema and workbook can appear to be an implemented refresh service if the distinction is not prominent. | Make delivery acceptance a first-class operator task: file, scope, counts, errors, changed objects, and acceptance receipt. Keep simulated comparisons labeled until an accepted snapshot actually drives the registry. |
| P1 | **Fact:** current workspace comparison uses one observation date and one completeness flag for the whole workspace. The monthly cadence is a product constraint. Do not silently increase a freshness limit to make indicators green. Choose limits for the question being answered. A month-old asset list may support an inventory report while failing a current-access verification question. Manual verification can close urgent work when allowed, with its own evidence and approval.

## 2. Three repaired defects to retain as regression cases

These source-level reproduction paths identified defects during review. Current source contains their repairs. Keep the scenarios in release checks; do not present them as current failures.

### P1 repaired: closing-evidence approval was absent from the queue

**Original defect:** the Review branch assigned `awaitingApproval: false` to every review. The approval view therefore omitted evidence-closure decisions. [Inbox construction and filtering](../src/utils/workItems.ts), [review form](../src/features/reviews/Reviews.tsx)

1. Use an open administrative review with resolution, verification method, verification date, and closing evidence.
2. Save those fields without a matching evidence-closure approval.
3. Open My work → Awaiting approval.

**Current result from the code:** valid closing evidence without its matching approval produces Awaiting closure approval and the action Approve closing evidence.

**Implemented repair:** the queue checks resolution, closing evidence, verification method, valid dates, and the exact `closureKey()`. Editing that evidence changes the approval context. Incomplete evidence does not enter the approval queue.

**Acceptance:** the case appears once in Awaiting approval; a changed evidence revision invalidates the pending decision context; an approved case offers closure without closing unrelated findings.

### P1 repaired: another person's draft was editable through its route

**Original defect:** the form relied on submission status and list filtering, without an actor-bound save guard. [Request list and form](../src/features/requests/Requests.tsx), [current command guard](../src/utils/workflowActors.ts)

1. Create or retain a draft owned and created by someone other than the simulated business actor P1.
2. Switch to Business view.
3. Open its direct `/requests/<id>` route and save an edit.

**Current result from the code:** an unrelated profile cannot save or submit the stored draft. The guard checks the stored creator and owner, rather than trusting edited values.

**Implemented repair:** `requestActorIssue()` checks an active actor, authorized stored responsibility, unchanged creator, and submitted immutability. The form uses it before and inside the update. The simulated P3 administrator remains explicit. Production must derive authorization from the authenticated command context.

**Acceptance:** an unrelated business user cannot save, submit, or replace the draft, including through a direct URL. The authorized creator, owner, and permitted administrator retain the intended access.

### P1 repaired: the email helper accepted duplicate directory evidence

**Original defect:** the helper checked distinct IDs and enabled values but accepted repeated identical candidate rows. The SQL handoff treated those duplicates as review evidence. [V1.1 helper](../src/domain/foundation.ts), [V1 matching query](../../platform-data-collection/v1-extract/sqlserver-email-match.sql)

1. Supply one platform email and a complete directory scope.
2. Supply two identical directory rows with that tenant, Mail, object ID, and enabled flag.
3. Call `resolveEmail()`.

**Current result from the code:** the helper returns Ambiguous directory evidence and routes the issue to Platform Manager.

**Implemented repair:** exactly one matching directory row is required. Group and application principals cannot resolve as a Person. Exact normalized SourceEmail-to-Mail matching remains scoped by tenant. Resolved-disabled remains separate from unresolved; no UPN fallback was added.

**Remaining acceptance before ingestion:** run shared fixtures through the SQL handoff, offline validator, and application helper. Include duplicate rows, conflicting states, reused email, missing tenant, disabled accounts, malformed identity values, and incomplete coverage. This review confirms the repaired helper branches; it does not establish complete equivalence across three runtimes.

The product-owner review should answer these elimination questions:

1. Can Register Existing omit editable setup fields until the user requests an actual change?
2. Can a no-change Standard request record one technical decision, while reusing its context for subsequent delivery evidence?
3. Can one dataset failure create one manager work item with linked impacts, instead of one task per affected object?
4. Can annual assurance use four explicit thematic confirmations with exception detail, while preserving every required answer?
5. Can monthly unchanged records and stable-key renames be accepted as a reviewed batch, leaving only material exceptions as individual work?

These questions concern unnecessary interaction and duplicated work. They do not reopen confirmed approval roles, tier order, manual PRL, the `_DS` purpose, identity matching, or retention.

## 4. Additional findings that affect trust and workload

### P2: annual response identity picker now duplicates the guarded actor

**Fact:** the form still displays a responding-Champion picker. The command now records the active current profile and validates that person's packet membership. [Annual form](../src/features/attestations/Attestations.tsx), [actor guard](../src/utils/workflowActors.ts)

**Inference:** the attribution defect is repaired. The picker can still imply that the user may act as someone else, even though the saved responder is fixed.

**Recommendation:** replace the editable picker with the current responder's read-only name and role. If recording on behalf of someone becomes necessary, design a separate command with recorder, respondent, and reason. That feature is not needed to meet the current requirements.

### P1: current risk rows do not come from the new delivery comparison

**Fact:** findings and their severity/results are initialized as mock fixtures. Workspace comparison evaluates separate mock evidence and configurable freshness. V1.1 `compareDelivery()` does not update findings. [Fixtures](../src/data/mock.ts), [comparison](../src/utils/logic.ts), [foundation](../src/domain/foundation.ts)

**Inference:** a workspace can show Unable to Verify in comparison while a related fixture still shows a conclusive discrepancy. That is acceptable demonstration data only if the screen explains it.

**Recommendation:** label fixture findings as illustrative. Show an evaluation receipt, selected input runs, and coverage before using findings as operational risk. Keep all eleven bucket definitions; activate only rules supported by accepted datasets. Unsupported coverage is information, not an invented failure.

### P2: the queue sorts due date before severity

**Fact:** `workItems()` sorts first by due date, then by severity. Missing dates sort last. [Queue ordering](../src/utils/workItems.ts)

**Inference:** an undated critical case can appear below a distant low-priority item. The interface says it is ordered by due date, so this is a product priority choice rather than a hidden sorting bug.

**Recommendation:** give the inbox an explicit urgent lane for accepted critical/high-impact cases, followed by dated obligations. Avoid generating Critical solely from a bucket name or missing metadata. Add a no-owner/no-due-date triage filter instead of burying these cases.

### P2: “all unresolved goes to Platform Manager” needs a work unit

**Fact:** routing is confirmed, but the source artifacts identify row-level exceptions. The runtime queue is made from requests, reviews, and annual records. It is not a demonstrated importer that groups source exceptions into cases. [Identity handoff](../../platform-data-collection/v1-extract/README.md), [work items](../src/utils/workItems.ts)

**Inference:** without stable grouping, each monthly delivery could regenerate work for the same unresolved person. With excessive grouping, unrelated conflicts could disappear inside one large task.

**Recommendation:** define case keys: source identity + issue type for person resolution, native relationship + issue type for missing links, and run/dataset/scope for collection failure. Preserve occurrences under the case. Count both open cases and affected objects. Show a real next action and accountable queue, not a generic “investigate” instruction.

### P1 repaired: Champion authority now separates current responsibility and frozen annual recipients

**Original defect:** `workspaceIdsFor()`, annual work assignment, packet capture, and fallback recipients used `requestedVersionId`. Current source now uses shared authority helpers across those paths. [Authority](../src/utils/authority.ts), [workspace responsibility](../src/utils/workItems.ts), [packet capture](../src/utils/attestation.ts), [response command](../src/utils/workflowActors.ts), [annual interface](../src/features/attestations/Attestations.tsx)

**Inference:** proposed Champions must not gain current work merely because a request names them. Existing annual recipients must not lose an issued task when the current roster changes.

**Implemented prototype repair:**

1. `currentChampionIds(data, workspace)` reads `implementedVersionId`. It never falls back to the requested version. This is the nearest accepted-baseline proxy in the current runtime.
2. Current workspace responsibility and new annual packet capture use that helper. Matching groups and people are captured with the packet.
3. `attestationRecipientIds(record, data)` prefers frozen `snapshot.championIds`. An explicit empty array remains empty.
4. Legacy packets without recipient IDs use only their captured implemented version. Missing historical assignments return no recipients; they never borrow a requested roster.
5. Annual queue visibility, assignment, due counts, recipient labels, form access, and commands reuse these helpers. Frozen recipients retain issued work after roster changes. Current owners can observe it; they can respond only when also selected recipients.

Keep the current active-status check for new responses. Preserve completed receipts and existing packet recipients. Do not silently recapture an old packet to make it fit the new rule. Explicit reissue should retain prior answers and decisions if legacy context needs correction.

**Acceptance cases:** a requested-only Champion gains no current responsibility; an implemented Champion retains it; a frozen recipient retains the issued annual task after a roster change; empty recipients do not expand access; missing baseline does not trigger a requested-roster fallback; a disabled recipient cannot submit; completed receipts remain unchanged.

**Remaining operating requirements:** `implementedVersionId` is a prototype proxy, not a complete business-acceptance policy. Persist when business responsibility becomes effective. Technical implementation and observed membership must not independently grant a declared business role. A packet with no recoverable recipients needs an explicit Platform Manager exception case; returning an empty list safely blocks a response but does not resolve the work. Follow-up evidence now keeps captured group context and routes to the current workspace owner. Preserve that distinction when adding accepted business versions.

### P2: monthly history needs a comparison baseline, not just storage

**Fact:** the V1.1 function preserves stable IDs and identifies older observations, but does not persist a selected dataset baseline or correction receipt. [Foundation comparison](../src/domain/foundation.ts)

**Inference:** “latest” can become ambiguous after a corrected or late delivery. A six-month file archive alone does not establish which snapshot supports a decision.

**Recommendation:** keep accepted delivery receipts and a current-dataset pointer per exact scope. A corrected delivery must identify what it supersedes. Preserve observations used by open work and active approvals beyond routine history cleanup. Do not replace the latest accepted state with a late older observation.

## 5. Required product invariants

These rules should be expressed once and reused by screens, SQL commands, and offline checks:

- An observed technical owner is not the declared Business Owner / Workspace Owner.
- A proposed Champion is not automatically the currently responsible Champion.
- A successful account match does not grant a business role or approval authority.
- A disabled matched account remains resolved; missing evidence is not inactivity.
- A request receipt is not proof that the registry and platform are reconciled.
- Complete inventory is not complete permissions, lineage, activity, or directory evidence.
- A recurring issue updates one stable case; a new extract is an occurrence, not automatically a new issue.
- A manual approved PRL requires its evidence; readiness inputs calculate no score.
- Tier 1 is highest, followed by Tier 2 and Tier 3.
- Closing one case changes only its explicitly linked findings.

The [12-table foundation](v1.1-model-simplification.md) supports these distinctions. Its reduced table count is useful only if the app's commands and views preserve the same meanings.

## 6. Recommended delivery sequence

1. **Make evidence acceptance real and narrow.** Validate one representative delivery, reconcile stable keys, retain unresolved rows, and record acceptance. Confirm the installed Alteryx backend mapping with actual output.
2. **Retain repaired workflow checks.** Approval queue visibility, actor-bound actions, assessment projection, and request wording now have repairs. Finish shared identity fixtures and preserve those regression cases.
3. **Operationalize accepted responsibility.** Retain the shared Champion helpers and frozen-packet checks. Add an explicit business-acceptance pointer and route unrecoverable packet recipients. Show the version used by each queue item.
4. **Remove unnecessary interaction.** Use exception-first registration, shared evidence context, and grouped manager work. Preserve required decisions and receipts.
5. **Resume Canvas implementation against the settled contract.** Port demonstrated behavior and verified data shapes. Do not carry known React shortcuts into the app as the operating specification.

The release should measure delivered value: accepted delivery rate, unresolved case age, repeat exceptions, median time to register an existing workspace, and approval waiting time. Do not use the number of completed forms as the primary success metric.

This review does not certify production readiness. It defines concrete repairs and work that can be removed while retaining the user's confirmed requirements.
